### Q1 · 6/15 ⚠️ 节点顺序对了一半，但**失败回退机制完全没答**

你答的 8 步基本对（节点名是意译的），对照一下：

| 你的答案 | 真实节点名 |
|---------|-----------|
| 1 初始化 yooasset | `FsmInitializePackage` ✅ |
| 2 获取最新版本号 | `FsmRequestPackageVersion` ✅ |
| 3 获取最新 manifest | `FsmUpdatePackageManifest` ✅ |
| 4 对比差异，没差异到 8 | `FsmCreateDownloader` ✅ |
| 5 下载 | `FsmDownloadPackageFiles` ✅ |
| 6 校验下载文件 | `FsmDownloadPackageOver` ⚠️（名字是"下载结束"，校验实际上是在每个文件下载过程里做的） |
| 7 清除缓存 | `FsmClearCacheBundle` ✅ |
| 8 开始游戏 | `FsmStartGame` ✅ |

**但你漏答了 "失败回退"这一半题目**。

YooAsset 的失败回退**不是自动 retry**，而是**UI-driven**：
```
FsmInitializePackage 失败
  → 发送事件 PatchEventDefine.InitializeFailed
  → UI 弹窗"失败，重试？"
  → 用户点击 → UI 发送 UserEventDefine.UserTryInitialize
  → PatchOperation.OnHandleEventMessage → _machine.ChangeState<FsmInitializePackage>()
```

**这是 YooAsset 设计的精髓**：状态机不做业务决策（要不要重试、停多久），把决策权交给 UI 层。这样做的好处是灵活（用户可选"取消/换网络/继续"），坏处是业务方需要自己接 UI 事件。

对比你的自研方案（重试 15 次 3 轮自动跑）：  
- ✅ 你的方案对用户更"傻瓜"
- ✅ YooAsset 方案对用户更"可控"

### Q2 · 5/10 ⚠️ 你提到了版本回退，但漏了更本质的原因

你的答案方向对（版本回退），但只抓到一个点。**完整的三个理由**：

1. **灵活性** —— 两步之间可以插自定义逻辑（弹窗提示新版本、埋点统计等）
2. **版本解耦** —— `UpdatePackageManifestAsync(packageVersion)` 接受的是**任意版本号**，不一定是 `RequestPackageVersionAsync` 返回的最新版。业务层可以：
   - 传最新版本号（正常流程）
   - 传写死的旧版本号（回滚）
   - 传 A/B 测试分配的版本号（灰度）
3. **缓存优化** —— 如果 `PackageVersion` 没变（上次已更新过），业务层可以直接跳过 Update 步骤，省一次网络请求

### Q5 · 4/10 ⚠️ "两种都一样"答对了，但没说出机制

你的直觉对（a 和 b 行为一致），因为**两种情况下进程都被杀，对文件系统而言没区别**。

YooAsset 的断点续传实现（对你来说应该很熟）：

```
下载中
  → bundle_xxx.tmp（临时文件，持续写入）

App 被杀（任意原因）
  → .tmp 文件保留在磁盘上（未删除未重命名）

下次启动
  → 检测到 .tmp 存在，读取已下载字节数 N
  → 发 HTTP 请求：Range: bytes=N-
  → 服务器返回 206 Partial Content，返回剩余部分
  → 追加写入 .tmp
  → 下载完成 → CRC 校验
  → 通过 → rename 为正式文件
  → 不通过 → 删除 .tmp 重新全量下（罕见）
```

**对比你的自研方案**：逻辑一致，没区别。区别在 **Bundle 粒度校验** —— YooAsset 每个 Bundle 都有 CRC，断点续传后的 CRC 不对就废弃重下。你以前项目是不是也这么做？

### Q6 · 9/10 ✅ **这题你是蒙的，但全蒙对了！**

你说"文档里有提到吗？" —— 其实 07 构建系统文档里有（你还没看到），但你**凭命名推理全答对**了：

```csharp
None                 → 不 Copy，Bundle 全走 CDN（零安装包方案）
ClearAndCopyAll      → 清空 StreamingAssets，全部 Copy 进包（全量首包）
ClearAndCopyByTags   → 按标签 Copy（混合方案，常用！只进新手村/首关资源）

**为什么叫 "Copy"**：因为构建输出的 Bundle 文件默认放在 `BuildOutputRoot`（比如 `D:/CDN/`），`BuildinFileCopyOption` 决定**构建完成后要不要把 Bundle 复制一份到 `Assets/StreamingAssets/` 下**（这样才能打进安装包）。

你推理对了一点没记住的：**ClearAndCopyByTags 是商业项目最常用的**，因为：
- 全量 Copy → 安装包太大（玩家看到 2GB 直接卸载）
- 不 Copy → 首次进游戏必须联网下载（体验差）
- 按 Tag Copy → 首关资源打包，其他 CDN 下载（兼顾体验和包大小）

### Q7 · 8/10 ✅ **思路对了，且考虑了时间切换**

你的方案：roll 0~10，小于等于 1 就走新版本，否则走 n-1 版本；超过 24 小时全量切。

方向完全正确，但有两个可以优化的点：

1. **不要用纯 Random.Range** —— 同一个玩家每次启动 roll 结果不同，会导致"昨天能进新版本，今天又切回旧版本"的抖动。应该用**设备 ID / 玩家 ID 的 hash** 取模，保证同一玩家结果稳定。

```

2. **"24 小时自动切换"容易出事故** —— 工业界灰度一般是**服务端控制**（灰度配置文件里写当前灰度比例，客户端拉取），万一线上发现问题可以从服务端 1 秒关掉灰度。时间硬编码客户端不可控。

对比你的自研方案，灰度这部分是典型的**服务端主导 + 客户端执行**。

### Q8 · 5/10 ⚠️ "覆盖版本号"方向对，但没说清"覆盖什么"

正确答案：
- **a) YooAsset 原生支持** ✅（只要 CDN 保留旧版本 Bundle 和 Manifest 就能回滚）
- **b) 具体操作**：

CDN 目录结构：
```
CDN/Android/v1.0/
  ├── PackageManifest_DefaultPackage_hashA.hash   ← 内容是 "1.0.20250101"
  ├── PackageManifest_DefaultPackage_hashA.bytes  ← Manifest 文件
  └── 各种 xxx.bundle
CDN/Android/v1.0/
  ├── PackageManifest_DefaultPackage_hashB.hash   ← 内容是 "1.0.20250105"
  ├── PackageManifest_DefaultPackage_hashB.bytes
  └── 各种 yyy.bundle
```

回滚操作：**把 `.hash` 文件（框架查最新版本号就读这个）里的内容改回旧版本号字符串**。客户端 `RequestPackageVersionAsync` 下次会拿到旧版本号，继而加载旧 Manifest，继而加载旧 Bundle。

**前提**：旧版本的 Manifest 和 Bundle 都还在 CDN 上没被清理（所以 CDN 要保留历史版本）。

### Q9 · 6/10 ✅ 排查思路合格，但遗漏了几个常见原因

你的思路对（看日志、版本号、manifest、下载记录），这是**工程师的基本素养**。  
但**两个常被忽视的原因**没想到：

1. **CDN 边缘节点缓存未刷新** —— 玩家访问的 CDN 节点缓存了旧的 `.hash` 文件，导致 `RequestPackageVersionAsync` 返回的是旧版本号。这是玩家"看似已更新实则加载旧资源"最常见的原因。
   - 验证：让玩家切网络（WiFi→4G，或 DNS 换成 8.8.8.8），强制命中另一个节点
   - 根治：发布时调用 CDN API 主动刷新 `.hash` 文件

2. **Manifest 下载成功但本地持久化失败** —— 极小概率，比如磁盘满了、权限问题，写新 manifest 失败但框架没检测到。可以排查 `persistentDataPath` 下该包的 Manifest 文件是否真的是 v2 的 hash。

3. **Bundle 文件未命中更新列表** —— 打包时这个 Bundle 配置了 `IncludeInBuild = false` 或 tag 错误，v2 的 Manifest 里指向了旧 Bundle hash。

你猜的"打包错误"其实就是 3，方向对，但缺细节。

## 📖 标准答案一览

**Q1. 8 个 FsmNode 顺序 + 失败回退**：
```
FsmInitializePackage   (失败 → InitializeFailed 事件 → UI 重试 → 回到 InitializePackage)
      ↓
FsmRequestPackageVersion  (失败 → PackageVersionRequestFailed → 重试)
      ↓
FsmUpdatePackageManifest  (失败 → PackageManifestUpdateFailed → 重试)
      ↓
FsmCreateDownloader    (无更新直接跳到 StartGame)
      ↓
FsmDownloadPackageFiles  (失败 → WebFileDownloadFailed → 回到 CreateDownloader)
      ↓
FsmDownloadPackageOver
      ↓
FsmClearCacheBundle
      ↓
FsmStartGame
```
**关键**：YooAsset 失败回退不是自动 retry，而是 **UI 驱动**（UI 弹"重试"→ 用户点击 → 发事件 → 状态机 ChangeState）。

**Q2. 为什么分两步请求**：
1. **灵活性** —— 两步之间可插入业务逻辑（弹窗、埋点、A/B 分流）
2. **版本解耦** —— `UpdatePackageManifestAsync(ver)` 接受**任意版本号**，可实现：
   - 传最新版（正常）
   - 传旧版（回退）
   - 传灰度版（A/B）
3. **缓存优化** —— 版本号没变可跳过 Update 一步

**Q3. 三种下载器 API**：

| API | 范围 | 场景 |
|-----|------|------|
| `CreateResourceDownloader(10, 3)` | 整包所有缺失 | 全量补齐 |
| `CreateResourceDownloader(tags[], 10, 3)` | 指定 tag 的资源 | DLC / 语言包 / 关卡包 |
| `CreateBundleDownloader(assetInfos, 10, 3)` | 精确指定资源及依赖 | 预下载单个 Boss / 关卡 |
（最精细是 `CreateBundleDownloader`）

**Q4. EFileClearMode 四种**：
```csharp
ClearUnusedBundleFiles        // 清理未在 Manifest 的旧 Bundle（最常用）
ClearAllBundleFiles           // 清理本包所有 Bundle（慎用）
ClearBundleFilesByTags        // 按标签清理（卸载 DLC 用）
ClearBundleFilesByLocations   // v2.3.18 新增：按资源地址清理
```

**Q5. 断点续传 half-dead 处理**：
- a/b 两种情况**行为一致**（进程都被杀，对文件系统没区别）
- 机制：`.tmp` 文件保留 → 下次启动检测 → HTTP `Range: bytes=N-` → 追加写入 → CRC 校验 → 通过则 rename 为正式文件
- 不通过则删 `.tmp` 重新全量下（罕见）

**Q6. BuildinFileCopyOption 三种**：
```
None                 → 不 Copy，Bundle 全走 CDN（零安装包）
ClearAndCopyAll      → 清空 StreamingAssets，全部 Copy（全量首包）
ClearAndCopyByTags   → 按标签 Copy（商业项目最常用，只进首关资源）
```
"Copy" 指的是**构建完成后把 Bundle 从 BuildOutputRoot 复制到 Assets/StreamingAssets/**。

**Q7. 灰度发布正确做法**：
- **不用纯 Random**（会抖动）
- 用**稳定分桶**：`hash(deviceId + packageName) % 100 < 灰度比例`
- 工业化：**服务端下发灰度比例**，客户端只执行，出问题可秒关

**Q8. 版本回退**：
- ✅ YooAsset 原生支持（前提：CDN 保留历史 Manifest + Bundle）
- **操作**：修改 CDN 上的 `.hash` 文件（框架查最新版本号的入口）内容为旧版本号字符串
- 客户端 `RequestPackageVersionAsync` 拿到旧版本号 → 加载旧 Manifest → 加载旧 Bundle

**Q9. "更新到 v2 加载 v1" 可能原因**：
1. **CDN 边缘节点缓存未刷新** ← 最常见！玩家访问节点缓存了旧 `.hash`
   - 验证：让玩家切网络（WiFi→4G）命中另一节点
   - 根治：发布时调 CDN API 主动刷新
2. **Manifest 下载成功但本地持久化失败** ← 磁盘满 / 权限
3. **Bundle 未进入新 Manifest** ← 打包配置 `IncludeInBuild = false` 或 tag 错误
4. **Bundle hash 碰撞** ← 极罕见但可能

**Q10. vs 自研对比**：

| 维度 | 自研 C++/Java/ObjC | YooAsset |
|------|-------------------|----------|
| 状态机 | 自己写 | 用 UniMachine 框架 |
| 异步调度 | 平台线程池 | 协程 + 每帧驱动 GameAsyncOperation |
| 文件 IO | C++ 直接 | C# + IFileSystem 抽象 |
| 重试 | 典型 15 次 3 轮自动 | 3 次 + UI 驱动 |
| 多包 | 多数没有 | 原生 Package 概念 |
| 限速/QoS | 常有 | **YooAsset 没有，业务层自己做** |
| 开发效率 | 低（要自己维护）| 高（开箱即用）|
| 极致性能 | 更强 | C# 够用 |
