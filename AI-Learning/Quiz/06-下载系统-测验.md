### Q3 · 10/10 ✅ 技术理由非常准

> "本地文件的 md5 和最新 manifest 的已经比对过了，不用再重复校验一次"

```csharp
if (downloader.TotalDownloadCount == 0)
{
    _machine.ChangeState<FsmStartGame>();  // 跳过下载阶段
    return;
}
```

### Q4 · 5/10 ⚠️ "查字典题"，但你对 Clamp 行为的判断对了

**`MAX_LOADER_COUNT = 64`**（源码 `DownloaderOperation.cs`）。

**为什么限制并发**：
1. **TCP 连接限制** — 安卓/iOS 单进程 TCP 连接数有限（通常 100-200），YooAsset 占用一部分就够了
2. **CDN 服务器防护** — 单客户端并发太高会被 CDN WAF 当 DDoS 封 IP
3. **移动端网络栈开销** — 线程切换 + TCP 握手成本，超过一定并发反而变慢
4. **RAM 限制** — 每个下载会有 Buffer，64 个 = 几 MB，已经不小

**传 1000 的结果**（你答对了）：
```csharp
// DownloaderOperation 构造函数里：
_downloadingMaxNumber = Mathf.Clamp(downloadingMaxNumber, 1, MAX_LOADER_COUNT);
// 所以 1000 → 64
```

框架自动 clamp，不会崩溃但也不会真的开 1000 个。

**工业经验**：
- 手机 4G/5G → 8~16 并发最佳
- Wi-Fi → 16~32
- 开 64 通常没有正收益（瓶颈转到 CDN 端）

**b) HTTP Range 头**（补上）：

**c) CDN 文件更新了（hash 变了）** ✅ 你答得很完整：

- 文件名包含 hash（`xxxx_<hash>.bundle` 或 hash 作为文件名）
- **所以旧的 `.tmp` 和新文件名不匹配，根本不会被当作断点续传的目标**

**这是 Hash 命名的一大设计优势** —— 不同版本的 Bundle **不会互相污染**，因为文件名就不同。

### Q7 · 6/10 ⚠️ 方向对但细节有出入

**Pause vs Cancel 的内部状态**：

| API | 内部行为 |
|-----|---------|
| `PauseDownload()` | 设置 `_isPause = true`，停止调度新下载任务，**正在跑的任务继续完成**。`.tmp` 文件保留 |
| `CancelDownload()` | 把 DownloaderOperation 标记为 **Failed 终止状态**，停止所有任务 |

**你的答案 1（暂停可恢复，取消从 0）** —— 前半对，后半有点偏差：
- 取消后**物理层面的 .tmp 文件还在磁盘上**（YooAsset 不会主动删）
- 但这个 **Downloader 实例已经死了**（Operation 进入终止态）
- 你要**重新 `CreateResourceDownloader(...)` 创建新 Downloader**
- 新 Downloader 遇到已有的 `.tmp`，**还是会断点续传**（HTTP Range）

**你的答案 3（取消后 BeginDownload 从 0）—— 不完全对**：
- 对 Cancelled Downloader 再调 `BeginDownload()` 基本**不会有效果**（Operation 已经 Done）
- 必须创建新 Downloader 才能继续
- 但新 Downloader 会自动利用 `.tmp`，不会真的从 0 开始下

**总结**：Cancel 终结的是 **Operation 对象**，不是磁盘文件。断点续传是文件层面的能力，只要 `.tmp` 还在就能续。

### Q9 · 7/10 ⚠️ b 和 c 对，a 的理解有偏差

**a) LoadAssetAsync 会等你的显式 Downloader 吗？**

你说"并行下载，毕竟是俩 downloader" —— **实际更微妙**：

- **Bundle 维度去重**：同一个 Bundle **不会被下载两次**（内部 `FSDownloadFileOperation` 级别去重）
- **如果 Boss 的 Bundle 已经在显式 Downloader 的队列里**：
  - LoadAssetAsync 发现 Bundle 正在下载
  - **会"挂靠"到那个已有的下载任务上**，不创建新任务
  - 等那个下载完了，LoadAssetAsync 的 Handle 也就成功了
- **如果 Boss 的 Bundle 不在显式队列里**：
  - LoadAssetAsync 会创建自己的隐式下载任务
  - 和显式 Downloader 并行（共用 64 的并发上限）

**所以 LoadAsset 不是"等" Downloader，而是和它"融合" —— 如果要的 Bundle 恰好在它的队列里。**

**b) 同一个 Bundle 会被下载两次吗？** ❌ **不会** ✅ 你答对了

**c) 进度互相影响** ✅ 部分对 —— 网速确实是共享的，但更精确的说法是"**共用 MAX_LOADER_COUNT=64 的并发槽位**"。不是严格"抢网速"，而是任务调度层面共用资源池。

**Q4. MAX_LOADER_COUNT**：  
- **值 = 64**（源码 `DownloaderOperation.cs`）
- 限制原因：TCP 连接数限制、CDN 防 DDoS、线程调度开销、RAM 占用
- 传 1000 会被 clamp：`Mathf.Clamp(downloadingMaxNumber, 1, MAX_LOADER_COUNT)` → 实际 64

**Q5. 断点续传跨启动**：
- a) 本地有 `bundle_xxx.tmp`（30MB 临时文件）
- b) HTTP 头：`Range: bytes=30000000-`，服务器返回 `206 Partial Content`
- c) 如果 CDN hash 变了：文件名变（hash 命名），旧 `.tmp` 和新文件名不匹配，**自动孤立**；下次 `ClearUnusedBundleFiles` 会把它清掉

**Q6. 四个回调对号入座**：

| 时机 | 回调 |
|------|------|
| 每帧更新进度 | `DownloadUpdateCallback` |
| 显示正在下载的文件名 | `DownloadFileBeginCallback` |
| 整个下载全部结束 | `DownloadFinishCallback`（通过 `Succeed` 字段判断成功/失败）|
| 某文件重试 3 次都失败 | `DownloadErrorCallback` |

**Q7. Pause vs Cancel**：

| API | 本质 | 对 Operation | 对磁盘 `.tmp` |
|-----|------|-------------|-------------|
| `PauseDownload()` | 软暂停（bool 标志）| 保持 Processing | 不影响 |
| `ResumeDownload()` | 清标志，继续调度 | 继续 Processing | 不影响 |
| `CancelDownload()` | 硬终止 | **Operation 死亡**，Status=Failed | 保留，不删 |

- Pause 后 Resume：能从断点继续
- Cancel 后 BeginDownload：**无效**（Operation 已死），必须 `CreateResourceDownloader` 新建一个。新 Downloader 会自动利用已有 `.tmp` 断点续传。

**Q8. 失败 UI 设计**：
- a) 错误码分级：🔴 可重试（网络抖）/ 🟡 需用户操作（无 WiFi）/ ⚫ 致命（磁盘满）
- b) 继续从 80% 下（断点续传）；UI 可选"累计制"（继续 80%→100%）或"增量制"（重试新进度条 0→100%）
- c) iOS 后台几分钟可能被 kill；回来后要检测下载状态，能 Resume 则继续，不能则重建 Downloader
- d) 下载前检测：`freeBytes < needBytes + 200MB~500MB buffer` → 提示清理；下载中写失败会触发 `DownloadErrorCallback`

**Q9. 边玩边下载 + 显式下载共存**：
- a) **不会并行跑两次**。如果 Boss 的 Bundle 已在显式队列里，LoadAssetAsync 会**挂靠到已有任务上**；如果不在，才创建自己的隐式下载任务
- b) **同一个 Bundle 全局去重**，不会下两次
- c) 共享 MAX_LOADER_COUNT=64 的并发槽位，本质是"调度层共享"，表现为"抢网速"

**Q10. vs 自研对比**：

| 维度 | 典型自研 | YooAsset |
|------|---------|----------|
| 并发控制 | 线程池 + Semaphore | 协程任务 + MAX_LOADER_COUNT clamp |
| 临时文件命名 | `<hash>.tmp` | 同样（hash 命名自带隔离） |
| 多文件冲突 | 天然无冲突 | 同样 |
| CRC 失败策略 | 删 + 重下 + 降级 Fallback | 类似：删 `.tmp`，重下，用完重试走 Error 回调 |
| **YooAsset 不如自研的地方** | — | ❌ 没有原生带宽限速<br>❌ 没有 QoS 分级<br>❌ 离线检测不精细 |
