## 🛠️ 环境配置

### Q：为什么 Rider 打开 YooAsset.cs 没有高亮、跳转不到定义？

**原因**：Rider 需要通过 Unity 生成的 `.sln` 打开项目，直接打开文件夹只是普通 C# 项目，没有程序集引用信息。

**修复**：
1. `Unity → Edit → Preferences → External Tools` → 选 Rider
2. 点 `[Regenerate project files]` 生成 `.sln` / `.csproj`
3. 用 **`Unity → Assets → Open C# Project`** 打开（不要用 Rider 的 Open Folder）
4. 打开后左下角应显示 "Unity Editor (已连接)"

---

### Q：Unity 应该打开 YooAsset 根目录还是 Sample 目录？

打开 **`/LearnYooAsset`（项目根目录）**。

- `Assets/YooAsset/` 是嵌入的 YooAsset 源码
- `Samples~` 的 `~` 是 Unity 约定的"忽略目录"，不会被编译
- 想跑 Sample 要把目录**复制**到 `Assets/` 下，Unity 才会编译

---

### Q：Rider 文件管理器为什么看不到根目录的 .md 文件？

Solution 视图只显示 `.csproj` 里登记的代码文件。

**切换到 File System 视图**（Project 面板顶部的下拉）就能看到全部文件，包括 `CLAUDE.md`、`AI-Learning/*.md` 等。

## 🎮 资源加载

### Q：`handle.Release()` 和 `sceneHandle.UnloadAsync()`，是一个同步一个异步吗？

**不是设计偏好问题，是底层操作的耗时决定的**。

| Handle 类型 | 卸载 API | 同步/异步 | 原因 |
|------------|---------|---------|------|
| AssetHandle / RawFileHandle / SubAssetsHandle / AllAssetsHandle | `Release()` | 同步 | 只改引用计数，几纳秒 |
| **SceneHandle** | **`UnloadAsync()`** | **必须异步** | Unity `SceneManager.UnloadSceneAsync` 本身异步；销毁几千个 GameObject 一帧做不完 |

**易踩的坑**：`SceneHandle` 不要调 `Release()`！`UnloadAsync()` 内部已经自动帮你做了 `Release` 的事（源码注释写明了）。

**类比**：这和 C++ 做资源系统的思路一样 —— 轻量操作立即返回，重量操作必须 async/callback。

---

### Q：SubAssetsHandle 加载图集里的图片好复杂，所有 UI 图片都要这样用吗？我在 Prefab 拼的 UI 也要写代码 load .png 吗？

**95% 的 UI 场景不需要碰 `SubAssetsHandle`**。

#### ✅ 场景 A：静态引用（绝大多数 UI 情况）

直接在编辑器里拖拽 sprite 到 Prefab 的 Image 上：

```csharp
// 运行时只需要加载 Prefab
var handle = package.LoadAssetAsync<GameObject>("UIHome");
yield return handle;
var ui = handle.InstantiateSync(canvasRoot);
// 完事！所有 sprite 自动显示，不用管！
```

**原理**：Prefab 对 Sprite 的引用是**序列化的 GUID 引用**。打 AB 包时 YooAsset 自动分析依赖（`UIHome.prefab → Atlas.spriteatlas → icon.png`），写进 Manifest。运行时加载 Prefab，框架自动加载依赖 Bundle。

#### ⚠️ 场景 B：动态换图（才需要 `SubAssetsHandle`）

运行时才知道要显示哪张图的情况：

```csharp
// 例：玩家等级变化 → 切换头像边框
var handle = package.LoadSubAssetsAsync<Sprite>("Assets/UI/AvatarFrames.png");
handle.Completed += h =>
{
    var sprite = h.GetSubAssetObject<Sprite>($"frame_level_{level}");
    avatarImage.sprite = sprite;
};
```

#### 🎯 判断标准

| 情况 | 用什么 API |
|------|-----------|
| 编辑器能拖的（UI 布局固定）| **啥都不用**，只加载 Prefab |
| 玩家数据驱动的图（头像、徽章、皮肤） | `LoadSubAssetsAsync` |
| 独立的 Sprite 文件（不在图集里）| `LoadAssetAsync<Sprite>` |

#### 💡 Bundle 依赖的天然限制

Bundle 是加载的最小单位，**不能只拉 Bundle 的一部分**。

后果：如果一个 2048×2048 的图集 Bundle 包含 100 张 icon，你的 Prefab 只用了 1 张，加载 Prefab 也会把整个图集 Bundle 拉进内存。

**优化策略**：
- 同一界面用到的图放同一个图集
- 大 UI 按模块拆图集（HomeAtlas / BattleAtlas / SettingsAtlas）
- 小 UI 用零散图片 + `LoadAssetAsync<Sprite>` 精确加载

## 🧱 构建系统

### Q：同一个 YooAsset 项目能打开 Sample 的 Collector 吗？为什么报 "Found multiple AssetBundleCollectorSetting files"？

**错误原因**：YooAsset 用 `AssetDatabase.FindAssets("t:AssetBundleCollectorSetting")` 扫描**全项目**，发现多于 1 个就报错。

**常见场景**：
- Unity 第一次启动时框架自动创建了空的 `Assets/AssetBundleCollectorSetting.asset`
- 又复制了 Sample 带进来一份（如 `Assets/Samples/Space Shooter/GameSetting/AssetBundleCollectorSetting.asset`）

**解决方法**：
1. Unity Project 窗口搜索栏输入 `t:AssetBundleCollectorSetting`
2. 保留一份（一般保留 Sample 的，可以学习现成配置）
3. 删掉其他的

**设计约束**：YooAsset 全项目只能有一份 `AssetBundleCollectorSetting`。多 Package 管理在这同一个文件内的 Packages 列表做，不是多文件。

---

### Q：Sample 复制进 Assets 后还报 "Invalid collect path : Assets/Samples/Space Shooter/..."

**原因**：Sample 里的 Collector 配置写死的是 Unity Package Manager 导入 Sample 的**标准路径**：
```
Assets/Samples/<DisplayName>/<Version>/<SampleName>/
```

手动复制时目录名不一致，就会触发路径校验失败。

**解决**：把 Sample 目录重命名成 `Assets/Samples/Space Shooter/`（和 Collector 配置一致），或者手动改每条 Collector 的路径。

### Q：Android 和 iOS 怎么分平台资源，按 Package、Group 还是 Collector 分？

**结论：99% 场景什么都不用配，少量平台特有资源用 Group + ActiveRule**

**场景 A（最常见）：Android/iOS 同一份 Asset，只是压缩格式不同**
- 什么都不配，同一份 Collector 配置
- 切换 `BuildTarget` 出两次构建（CI 两条流水线）
- Unity 根据平台用 ASTC（Android）/ PVRTC（iOS）自动生成不同 Bundle
- CDN 按平台分目录：`CDN/Android/...` / `CDN/iOS/...`
- `IRemoteServices` 按 `Application.platform` 返回不同 URL

**场景 B：少量平台特有资源（不同 Shader、不同图标格式）**
- 建独立 Group，用 **ActiveRule** 按平台开关：
```
DefaultPackage
  ├── Group: Common             （所有平台）
  ├── Group: Android_Specific   （ActiveRule 写自定义"仅 Android"）
  └── Group: iOS_Specific       （ActiveRule 写自定义"仅 iOS"）
```

**场景 C（基本不用）：完全独立业务，按 Package 分**
- 运行时切换 Package 复杂度高，只有"两平台跑不同游戏"的罕见场景才考虑

**不能做的**：按 Collector 分 —— Collector 没有 ActiveRule，平台差异只能放在 Group 层

### Q：ActiveRule 只有 EnableGroup / DisableGroup，没有"仅 Android"选项

**YooAsset 内置只有两种**（都在 `DefaultActiveRule.cs`）：
```
EnableGroup      ← 默认，始终激活
DisableGroup     ← 永久禁用（临时屏蔽某 Group 用）
```

**要按平台激活，必须自己写一个 `IActiveRule` 实现**：

```csharp
[DisplayName("仅 Android 激活")]
public class ActiveRule_AndroidOnly : IActiveRule
{
    public bool IsActiveGroup(GroupData data)
    {
        return EditorUserBuildSettings.activeBuildTarget == BuildTarget.Android;
    }
}
```

放在任意 Editor 目录（必须 Editor 程序集），YooAsset 启动时**自动扫描所有 `IActiveRule` 实现类**，下拉框就能选到这个自定义规则了。

**同理可以写**：`IPackRule`（自定义打包规则）、`IAddressRule`（自定义地址规则）、`IFilterRule`（自定义过滤规则），都走同样的反射机制。

**位置：最右侧 Collectors 面板的顶部，在 Group Name 上方**。

Collector 窗口是三栏布局：

```
┌──────────┬──────────┬─────────────────────┐
│ Packages │  Groups  │ Collectors          │
│          │          │ ┌─────────────────┐ │
│  Default │  - UI    │ │ ActiveRule: [▼] │ │ ← ★ 这里
│          │  - Audio │ ├─────────────────┤ │
│          │          │ │ Group Name: UI  │ │
│          │          │ │ Asset Tags: ... │ │
│          │          │ ├─────────────────┤ │
│          │          │ │ Collector 列表  │ │
│          │          │ └─────────────────┘ │
└──────────┴──────────┴─────────────────────┘
```

看不见的两个可能：
- 窗口被拉得太窄（顶部这行被压没了）
- 没选中 Group（右侧面板只有选中 Group 才显示）

### Q：StaticAsset 和 DependAsset 都不能被代码加载，区别到底是啥？

**核心区别不是"能不能 Load"，而是"打包条件"不同**：

| 类型 | 进 Bundle | 有 address | 打包条件 |
|------|----------|-----------|---------|
| `MainAsset` | ✅ | ✅（代码可 Load）| 无条件 |
| `StaticAsset` | ✅ | ❌ | **无条件**（扫到就打）|
| `DependAsset` | 视情况 | ❌ | **有条件**：只有被 MainAsset 引用才打 |

**C++ 类比**：
- `MainAsset` = `extern` 函数（外部可调用）
- `StaticAsset` = `static` 函数（二进制里存在，不暴露符号）
- `DependAsset` = 未引用就被链接器优化掉的库函数

**用例区分**：一个文件夹里有 10 个 Shader，3 个没被 Material 使用：
- 配 `StaticAsset` → 10 个全打
- 配 `DependAsset` → 只打 7 个（孤儿自动剔除）

**决策**：
- Prefab / 场景 / 配置 → `MainAsset`（代码要 Load）
- Shader / 全局 Settings / 字体 → `StaticAsset`（要进包但代码不 Load）
- Texture 只被 Prefab 引用 → **不用配**，框架自动分析

---

### Q：那为什么"打包"和"可加载"是两件事？一个资源进了 Bundle 为什么不能直接 Load？

**打包 ≠ 暴露地址**。

```
打包：资源的二进制进 Bundle 文件里（物理层）
加载：业务代码能通过 address 在 Manifest 里查到它（逻辑层）
```

Shader 的典型使用链路：
```
LoadAsset<GameObject>("Player")   ← 业务代码 Load Prefab
  ↓ Player.prefab 里有
MeshRenderer
  ↓ 引用
Material
  ↓ 引用
Shader                            ← 全程没被代码直接 Load
```

Shader 需要进 Bundle（让 Material 能找到它），但**没人会写 `LoadAsset<Shader>("MyShader")`**，给它 address 纯浪费（Manifest 多一条记录 + 地址冲突风险）。

`StaticAsset` 就是"进包但不给地址"的身份 —— 相当于 C++ `static` 函数。

### Q：既然 Texture 被 Prefab 引用能自动打包，Shader 为什么还要单独用 StaticAssetCollector？

**理论上可以自动打包（99% 情况）**，YooAsset 甚至内置了 **"Auto Collect Shaders"** 开关（Collector 窗口 "Package Settings" 里默认开着）。

但 Shader 有几个 Unity 历史坑，纯依赖分析看不出来：

1. **`Shader.Find()` 动态加载**
   ```csharp
   var shader = Shader.Find("Custom/FancyEffect");  // 构建时扫不到这个字符串
   ```
   Shader 只被 `Shader.Find` 引用 → 依赖分析认为是孤儿 → 不打包 → 运行时紫红色报错

2. **URP/HDRP 的 Shader Variant Stripping**  
   构建时激进剥离"未使用的变体"，运行时 `EnableKeyword` 切换变体时发现变体不存在 → 渲染异常

3. **运行时动态创建 Material**  
   `new Material(shader)` 时 Shader 不是通过 Material Asset 被引用，依赖链反推不到

4. **后处理 / RenderFeature Shader**  
   被渲染管线配置引用，不在 Prefab 里

**对比 Texture**：Texture 几乎总是被 Prefab/Material **静态引用**，依赖分析 100% 可靠；Shader 有大量"代码 → Shader"的动态路径，分析有盲区。

**实战建议**：
- 小项目 / demo → 靠 `Auto Collect Shaders` 就够了，什么都不配
- 遇到紫红色模型 / Shader missing → 加 `StaticAssetCollector` 显式收集
- 商业项目 / URP 重度使用 → `StaticAssetCollector` + `PackShaderVariants` + Shader Variant Collection 三重防御

Space Shooter Sample 用 `StaticAssetCollector` 收 Shader 是**防御式**做法，不是必须。

### Q：配置表（不被 Prefab 引用，要代码加载）应该用 Main 还是 Static？

**答：MainAssetCollector**，毫无疑问。

判断标准只有一个：**代码要不要主动 Load 它**。

| 资源 | 代码主动 Load？ | CollectorType |
|------|---------------|---------------|
| Prefab / 场景 | ✅ | Main |
| **配置表（JSON / ScriptableObject）** | ✅ | **Main** |
| Shader | ❌（间接被 Material 引用）| Static |
| 字体 | 看情况 | Main / Static |

**"不被 Prefab 引用" 只影响依赖分析，不影响 Main/Static 判断**。配置表和 Prefab 是**两个独立的根**，它们各自是自己依赖链的起点。

**PackRule 选型**：
- JSON / 二进制配置 → `PackRule = PackRawFile`，用 `LoadRawFileAsync` 拿字节数组直接 parse
- ScriptableObject 配置 → `PackRule = PackSeparately`，正常 AB 打包，用 `LoadAssetAsync<ConfigSO>(...)`

### Q：Texture 被多个 Prefab 共享会资源冗余，怎么办？

**会冗余** —— 如果不处理，同一张 Texture 会被打进每个引用它的 Bundle，CDN 上存 N 份。

**这是 AssetBundle 系统的老难题**：资源引用关系是**图（DAG）**，但 Bundle 只能是**树**。被多父节点引用的子节点要么冗余，要么单独打包。

#### YooAsset 的三种处理方式

**方式 A（推荐）：`EnableSharePackRule = true`**

```csharp
buildParameters.EnableSharePackRule = true;         // 自动识别共享资源
buildParameters.SingleReferencedPackAlone = true;   // 单引用资源也独立打
```

YooAsset 构建时自动分析所有 MainAsset 的依赖：
- 被 2+ 个 MainAsset 引用 → 自动打到**共享 Bundle**
- 只被 1 个 MainAsset 引用 → 打进那个 MainAsset 的 Bundle

**不用手动配任何 Collector**。

**方式 B：手动 `DependAssetCollector`**

想显式管理共享资源目录时用。不如方式 A 省事，但更可控。

**方式 C：`StaticAssetCollector`**（不推荐用于 Texture）

无条件强制打包，可能打进用不到的资源，包体积膨胀。只适合 Shader 这种需要防御式打包的场景。

#### 推荐的处理顺序

1. **优先：自动分析**（`EnableSharePackRule`）—— 最省事
2. **不满意时：手动拆分** —— 如果自动结果的包大小 / 数量不理想（太碎或太大），再上 `DependAssetCollector`
3. **极端场景：StaticAsset**

#### 回到 Q2 原题

Q2 题干是"Texture **只被某个 Prefab 引用**" —— 单引用，不用单独配 Collector，框架自动打进 Prefab Bundle。

如果改成"被 N 个 Prefab 共享" —— **开 `EnableSharePackRule`** 或配 `DependAssetCollector`。

### Q：混合方案（APK 内置首关资源 + 其他 CDN）为什么不用 `None` + Unity Resources？

**核心原因：Resources 完全无法热更，StreamingAssets + YooAsset 可以被 CDN 版本覆盖**。

两种方案表面上都能"把首关资源放进 APK"，但后续维护能力差异巨大。

#### 关键差异：热更新能力

| 方案 | 打进 APK | 能热更 | 维护 |
|------|---------|-------|------|
| Resources 里放首关 | ✅ | ❌ **永远锁死** | 改了必须出新 APK 重下 |
| StreamingAssets（ByTags）| ✅ | ✅ **CDN 可覆盖** | 推个 CDN 包下次启动就修复 |

#### YooAsset 的"首包覆盖机制"

_（⚠️ 这里之前写的"先 Cache 后 Buildin"是错的，查源码后已纠正；详细机制见下面"HostPlayMode 查找顺序"的问答）_

```
加载 "Level1/Boss" 时（源码实现）：
  1. 先问 Buildin：Bundle 的 hash/GUID 在首包 catalog 里吗？
     - 在 → 用首包版本
     - 不在 → Buildin 拒绝，继续
  2. Cache 兜底（永远 Belong=true）
     - 本地缓存有 → 直接用
     - 本地缓存没有 → NeedDownload 触发 CDN 下载
```

**APK 原本有 `boss_hashA.bundle` → CDN 推新版 `boss_hashB.bundle`**：
- 新版 hash 不同 → GUID 不同 → 首包 catalog 里没有 hashB
- Buildin 拒绝 → Cache 兜底接手 → 下载新版
- 老版 `boss_hashA.bundle` 虽然仍在首包里，但**没有 Manifest 引用它了**，相当于被"逻辑遗弃"

**所以"首包覆盖"不是"Cache 优先读取"实现的，是"新版 hash 不同 → 首包查不到 → 自动走 Cache"实现的**。

#### 其他原因

1. **API 一致性** —— 业务代码不想混用 `Resources.Load` 和 `package.LoadAssetAsync` 两套
2. **内存占用** —— Resources 启动时全扫描索引；YooAsset Bundle 按需加载
3. **Unity 官方态度** —— 2019+ 起不推荐大量使用 Resources

#### Resources 应该放什么

只放"**启动时框架还没初始化就要用的**极少量资源"：
- `PatchWindow.prefab` —— 热更新进度 UI
- `LoginWindow.prefab` —— 首次登录界面（偶尔也放 YooAsset）

**游戏玩法资源（包括首关）绝对不要放 Resources** —— 因为一定会迭代，Resources 无法迭代。

### Q：ClearAndCopyByTags 说是"商业项目最常用"，但我玩的二次元手游都是零安装包？

**你的观察对** —— 现代二次元手游基本都是 `None` 零安装包方案，YooAsset 文档的说法可以理解为"比 CopyAll 更灵活"而非"当下主流"。

#### 主流二次元手游都是零安装包

| 游戏 | APK 大小 | 首次下载 |
|------|---------|---------|
| 原神 | ~300MB | 十几 GB |
| 崩坏：星穹铁道 | ~300MB | 5~8GB |
| 鸣潮 | ~200MB | 10+GB |
| 明日方舟 | ~100MB | 几 GB |

#### `None` 现在主流的原因

1. **包大小是应用商店排名因素** —— 小包下载转化率更高
2. **资源迭代频繁** —— 首包资源很快过时，没必要塞 APK
3. **用户习惯了"首次下载"** —— 原神的下载动画甚至成了梗
4. **运营灵活** —— 不受 APK 发布节奏束缚

#### ByTags **以前**常用的场景（现在少了）

1. **Google Play / App Store 早期包大小限制**（150MB 限制，现在 AAB 放宽到 200MB，iOS 4GB）
2. **3G/4G 时代下载慢**（现在 5G/Wi-Fi 普及，容忍度高）
3. **单机游戏 / 买断制手游**（本来就不更新）

#### ByTags 剩下的真实场景

1. **偏单机的休闲手游**（卡牌、消除）
2. **出海项目的首发阶段**（东南亚/印度/非洲网络差）
3. **小程序游戏**（但用的是平台分包机制，不是 YooAsset 的 ByTags）

#### 选型建议

| 项目类型 | 推荐 |
|---------|------|
| 二次元抽卡 | `None`（跟主流）|
| MMO | `None` |
| 卡牌 / SLG | `None` 或 `ByTags` |
| 休闲小游戏 | `ClearAndCopyAll`（包小）|
| 单机买断制 | `ClearAndCopyAll` |
| 小程序 | 平台分包 |

**二次元手游闭眼 `None`，你的直觉和市场一致**。

### Q：IFileSystem 的 5 个 bool 方法互相有包含关系吗？NeedUnpack 什么时候用？

_（下面所有断言都查过源码 `DefaultCacheFileSystem.cs` / `DefaultBuildinFileSystem.cs` / `PlayModeImpl.cs`）_

#### 五个 bool 方法的依赖关系

**`Belong` 和 `Exists` 是原子查询，互不调用**。`NeedDownload` / `NeedImport` 是**组合糖**，内部调用 Belong 和 Exists：

```csharp
// DefaultCacheFileSystem.cs 源码
public bool Belong(PackageBundle bundle) { return true; }   // 保底 FS
public bool Exists(PackageBundle bundle)
    => _records.ContainsKey(bundle.BundleGUID);

public bool NeedDownload(PackageBundle bundle)
{
    if (Belong(bundle) == false) return false;
    return Exists(bundle) == false;             // Belong && !Exists
}
public bool NeedImport(PackageBundle bundle)
{
    if (Belong(bundle) == false) return false;
    return Exists(bundle) == false;             // 逻辑同 NeedDownload，语义不同
}
public bool NeedUnpack(PackageBundle bundle) { return false; }  // Cache 不解压
```

**`NeedUnpack` 不走这个模板**，有自己的逻辑（见下）。

#### 关系矩阵（三种 FS 对照）

| 方法 | CacheFS | BuildinFS | 语义 |
|------|---------|-----------|------|
| `Belong` | 永远 true | 查 `_wrappers` 首包 catalog | 原子 |
| `Exists` | 查 `_records` | 查 `_wrappers` | 原子 |
| `NeedDownload` | `Belong && !Exists` | 永远 false（首包不下载）| 组合糖 |
| `NeedUnpack` | 永远 false | 见下（Android/OH 特殊逻辑）| 特殊 |
| `NeedImport` | `Belong && !Exists` | 永远 false | 组合糖，小游戏用 |

#### NeedUnpack 真实触发条件（源码）

```csharp
// DefaultBuildinFileSystem.cs:361
protected virtual bool IsUnpackBundleFile(PackageBundle bundle)
{
    if (Belong(bundle) == false) return false;

#if UNITY_ANDROID || UNITY_OPENHARMONY
    if (bundle.Encrypted)
        return true;                                          // ① 加密 Bundle
    if (bundle.BundleType == (int)EBuildBundleType.RawBundle)
        return true;                                          // ② 原生文件
    return false;
#else
    return false;                                             // 其他平台永远不解压
#endif
}
```

**真实触发条件（和文件大小无关）**：
- 只在 **Android / OpenHarmony** 平台触发
- 只对**加密 Bundle** 或 **RawBundle（原生文件，如 JSON / 视频 / 二进制）**

**为什么只有这两类要解压**：
- **加密 Bundle**：Unity `AssetBundle.LoadFromFile` 不认识加密过的数据（因为 AB 的二进制结构被改了），必须先解密写盘再加载
- **RawBundle**：不是 AssetBundle 格式（用户自定义文件），Unity 的 AB API 不认识，必须以文件形式落盘读
- **普通未加密 AB**：Android 可以用 `AssetBundle.LoadFromFile("jar:file:///...apk!/assets/...")` 从 APK 内直接加载，不用解压

#### 框架怎么调用（源码调用链）

```csharp
// PlayModeImpl.cs:229 —— 框架先找归属 FS
public IFileSystem GetBelongFileSystem(PackageBundle bundle)
{
    foreach (var fs in FileSystems)    // Buildin 先，Cache 后
        if (fs.Belong(bundle))
            return fs;                  // 第一个说 Belong=true 的就是它
    return null;
}

// 然后根据归属 FS 的 NeedXxx 决定流程
if (fs.NeedDownload(bundle)) 触发下载
if (fs.NeedUnpack(bundle))   触发解压
if (fs.NeedImport(bundle))   触发导入（小游戏）
```

### Q：HostPlayMode 查找顺序到底是 Buildin 优先还是 Cache 优先？

_（⚠️ 之前我写错过"Cache 优先"，查了源码后纠正）_

**源码真相：Buildin 先，Cache 兜底**。

```csharp
// ResourcePackage.cs:120 传入顺序
playModeImpl.InitializeAsync(
    BuildinFileSystemParameters,   // 先传
    CacheFileSystemParameters      // 后传
);

// PlayModeImpl.cs:33-41 按顺序塞入 FileSystems 列表
fileSystemParamList.Add(BuildinParams);
fileSystemParamList.Add(CacheParams);

// PlayModeImpl.cs:229 按列表顺序问 Belong
foreach (var fs in FileSystems)
    if (fs.Belong(bundle)) return fs;
```

**两个 FS 的 `Belong` 行为完全不同**：
- **Buildin**：查首包 catalog（`_wrappers` 字典），命中才归它
- **Cache**：源码注释明确写"**保底加载**"，永远返回 true

**真实判定过程**：
1. Buildin 先问："Bundle 在首包 catalog 里吗？" → 在就归 Buildin
2. Cache 兜底：Buildin 拒绝的都归 Cache（可能触发下载）

### 那热更新怎么工作？

**关键**：Bundle 按 hash 命名，新版 hash 不同 → `BundleGUID` 不同：

```
首包 boss_hashA.bundle   → GUID=hashA → Buildin catalog 里有
CDN 推新版 boss_hashB.bundle → GUID=hashB → Buildin catalog 里没有
                                             ↓
                                       Buildin.Belong 拒绝
                                             ↓
                                       Cache 兜底
                                             ↓
                                       Cache.Exists = false
                                             ↓
                                       NeedDownload = true 触发下载
                                             ↓
                                       下载到 persistentDataPath
```

**所以热更新的本质不是"Cache 优先覆盖 Buildin"，而是"新版 Bundle 的 hash 不同 → 首包 catalog 查不到 → 自动落 Cache 兜底"**。Cache "保底"的设计就是为了吞掉所有非首包资源。

#### 我之前错在哪

直觉上"Cache 优先"听起来合理（新版覆盖老版嘛），但源码不是这么实现的。真实机制更优雅 —— **靠 hash 命名避免了"优先级"的概念**，同一个逻辑 Bundle 的不同版本在物理层就是不同文件，各有归属。

### Q：UISpriteAtlas 和 UISprite 分开打 Collector，它们 Bundle 里到底各装了什么？

_（⚠️ 这个问题我之前凭直觉回答过一版，说"两个大小量级相近，存的都是像素，冗余了"—— 用户实测打脸：Atlas Bundle 只有 2k，UISprite Bundle 200k。下面是实测校准后的正确答案）_

#### 实测数据（Space Shooter Sample 打包后）

```
UISpriteAtlas Bundle:     2k   ← 几乎没内容
UISprite Bundle:        200k   ← 存了实际像素
```

#### 两个 Bundle 的真实内容

| Bundle | 大小量级 | 内容 | 作用 |
|--------|---------|------|------|
| **UISpriteAtlas** | **小**（几 KB）| SpriteAtlas 对象的**元数据**：sprite 名字 → 在哪张散图的哪个 `Rect(x,y,w,h)` | 对外的"查找入口" |
| **UISprite** | **大**（几百 KB ~ MB）| 散图的**实际 Texture 像素数据** | 实际的图片仓库 |

**核心认知**：**Atlas 本身不包含像素**，它只存"指针"（sprite 名字 → 散图引用）。像素永远在散图 Bundle 里。这和 Unity Sprite Atlas V1（独立打大纹理）**不同** —— V2 把数据和索引拆开，让 AB diff 更友好（改一张 icon 只影响那张散图 Bundle，不影响 Atlas 元数据）。

#### 所以两个 Bundle 是"协作关系"，不是"冗余关系"

运行时加载流程：
```
LoadAsset<SpriteAtlas>("ui_atlas")
  → 从 UISpriteAtlas Bundle 拿到 2k 元数据
  
atlas.GetSprite("icon_home")
  → 元数据查表："icon_home" 在 UISprite Bundle 的 icon_home.png 中
  → 加载 UISprite Bundle（200k）→ 拿到实际像素
```

**缺一不可**：
- 没 UISprite Bundle → Atlas 指针悬空，GetSprite 返回 null，UI 白屏
- 没 UISpriteAtlas Bundle → 代码无法通过 atlas 名字查找

所以 Sample 把 **UISprite 配成 Static**（让散图进包，供 Atlas 引用）、**UISpriteAtlas 配成 Main**（代码可 Load 的入口），是**必需**的配置，**不是我之前误说的防御式冗余**。

#### 为什么要分两个 Collector 而不是一个

因为 CollectorType 需要不同：
- Atlas 要 Main（代码要通过地址 Load 它）
- 散图要 Static（进包但不对外暴露地址）

一个 Collector 只能配一种 CollectorType，所以必须分开。

#### 如果项目真的想"Atlas 自包含"怎么办？

在 Unity 的 SpriteAtlas Inspector 里勾 **"Include in Build"** —— 这个是 **Unity 系统级**的机制，和 YooAsset 的 Collector 无关。勾了之后：
- Unity 把散图像素"烘焙"到 Atlas 内部（和 V1 行为类似）
- 可以不配 UISprite 的 Collector
- 但 Atlas Bundle 会变大

Sample 没勾这个开关（所以散图必须单独配 Static），这样 diff 粒度更细，也是当前主流做法。

#### 本次校准的方法论

**实测 > 直觉**。我一开始凭 Sprite Atlas V1 的印象判断"Atlas 装大图，数据冗余"，但用户实际打了包看到 2k / 200k 的对比才揭示真相。这也再次验证了笔记末尾那条原则："**断言如果涉及运行时行为，都应该和实测比对后再写**"。
